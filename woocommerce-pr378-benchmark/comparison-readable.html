How The Test Was Conducted

The measured window starts after restore, server startup, login setup, and warm-up.

  1. Build one fresh WordPress site per selected database variant from the same downloaded WordPress package.
  2. Generate the same seeded content fixture for each site: posts, pages, comments, users, postmeta, terms, and options.
  3. Create a database snapshot for each variant after fixture generation.
  4. For every measured case, restore that variant's clean snapshot before starting the server.
  5. Start local nginx and PHP-FPM for that one case, then prepare logged-in worker sessions outside the measured window.
  6. Run a concurrent warm-up period so first-request and cache effects do not dominate the measured result.
  7. Capture baseline counts after warm-up, then run the measured workload for the configured duration and configured number of concurrent requests.
  8. Execute user-flow loops: public reads, admin reads, comment writes, admin post updates, and profile updates depending on workload mix.
  9. Verify writes in-flow and again by post-run count deltas; only verified writes count toward write throughput.
  10. Record per-case request logs, Server-Timing data, failures, write effects, SQLite WAL size, SQLite lock messages, and MariaDB status counters.
  11. Repeat each workload/concurrent-request/variant cell three times and report medians.

What Was Compared

These definitions apply to every table below.

Database Variants

  • MariaDB baseline: WordPress Core using the local MariaDB/InnoDB database.
  • SQLite rc3: WordPress Core using SQLite Database Integration v3.0.0-rc.3.
  • SQLite stable: WordPress Core using SQLite Database Integration v2.2.23 as the stable-line control.
  • SQLite PR #378: WordPress Core using SQLite Database Integration PR #378, parser + lexer performance branch.

Workload Mixes

  • read-heavy: 90% catalog browsing/search and 10% logged-in order-admin reads; no checkout writes.
  • balanced: 50% catalog browsing/search, 20% add-to-cart flows, 20% checkout/order writes, 10% order-admin reads.
  • write-heavy: 20% catalog browsing, 20% add-to-cart flows, 50% checkout/order writes, 10% order-admin reads.

How To Read The Numbers

Comparison rows are written from SQLite rc3's point of view. For throughput columns, positive is good for SQLite and negative is bad. For latency columns, negative is good for SQLite because lower latency is faster.
  • Flows/s: completed user-flow loops per second. Higher is better.
  • Avg flow: average full user-flow loop completion time. Lower is better.
  • Avg HTTP request: average individual HTTP request completion time inside those flows. Lower is better.
  • p50 / p75 / p95 / p99: full-flow duration percentiles. p50 is the median, p95 is the slowest 5% boundary, and p99 is the slowest 1% boundary. Lower is better.
  • Write/s: verified write flows per second. Higher is better.
  • Write p95: 95th percentile duration for write flows only. Lower is better.
  • SQLite lock errors: logged SQLITE_BUSY, SQLITE_LOCKED, or database-is-locked messages. Zero does not mean zero waiting; it means no visible lock failures were logged.

Methodology Fixes In This Run

These are the fixes that make this run comparable to the suspicious earlier result.

  • database snapshot restored before every measured case
  • login/setup excluded from measured elapsed time
  • concurrent warm-up before measured window
  • three repetitions by default
  • variant alternation disabled because low-disk mode runs one variant at a time
  • verified WooCommerce checkout/order write flows
  • per-case request logs
  • SQLite WAL sampled without pre-recording checkpoint
  • database snapshots compressed to reduce benchmark artifact disk usage
  • low-disk mode: variants executed sequentially and cleaned up after completion
